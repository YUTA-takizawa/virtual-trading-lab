# Virtual Trading Lab — ルールベース仮想売買シミュレーター群

日本株・米国株・暗号資産を対象に、「相場の8箇条」（藤本茂氏の逆張り・待ちの売買規律）をベースにしたルールに従って架空資金で売買を模擬し、Discordへの通知と静的ダッシュボードで成績を追跡するプロジェクト。**実際の証券口座での自動売買は一切行わない**。

[YUTA-takizawa/house-scraper](https://github.com/YUTA-takizawa/house-scraper)（不動産新着通知＋個人用生活・資産管理Bot）から、2026年9月にこの仮想売買部分だけを切り出した。理由はGitHub Actionsの実行頻度（暗号資産版は15分おき等）がプライベートリポジトリの無料枠を圧迫したため——ここで扱うのは公開情報の候補銘柄と架空資金の仮想ポジションのみで実際の保有株情報を含まないため、Public化してActionsを無料枠なしで動かせるようにした。

## セットアップ

1. **Discord Webhookを1つ作成する**（専用チャンネルを1つ用意し、Webhookを作成）
   - チャンネルの設定 → 連携サービス（Integrations） → ウェブフック → 新しいウェブフック
   - `.env`（ローカル用）と GitHub Secrets（本番用）の両方に `DISCORD_WEBHOOK_DAYTRADE` として登録する
   - 機能1〜6すべてが同じWebhookを流用する（同じチャンネルにembedの色・タイトルを変えて投稿し、見分けられるようにしている。チャンネルを分けたい場合は各`index.ts`の`DISCORD_WEBHOOK_DAYTRADE`参照箇所を専用の環境変数に差し替えること）。機能4・5はルーチンの成績通知はしないが、致命的エラー時のみ同じWebhookでアラートを送る

2. **`config/` の記入**
   - `config/daytrade.json` — 機能1（日本株デイトレード・シミュレーション）の候補銘柄リスト（日経225の代表銘柄・日経500・JPXプライム150の構成銘柄などから527銘柄）、`virtualCapitalYen`/`maxPositionYen`（架空の元本・1銘柄あたりの取得コスト上限。1:2:6は100株単位の口数比率なので、1〜3段階目の合計は銘柄の株価次第でこの額を下回ることはあっても、超える場合はその回の購入自体を見送る）、`marginMultiplier`（1が現物同等。デフォルトのまま推奨。追証・金利は計算しないシンプルなモデル）、`thresholds`（急騰・急落・RSI・出来高・PER/PBR上限・`stopLossPct`=ストップロス%〈`0`で無効、デフォルト無効〉・`tranche2ConfirmPct`=追撃買いの確認閾値）。**『会社四季報』の内容（成長性コメント等）は東洋経済新報社の有料著作物のため使用しない**——PER/PBRという公開されている数値指標のみをYahoo!ファイナンスの公開ページ（`finance.yahoo.co.jp`）からスクレイピングして代替に使う。決算発表日も同ページから取得するが、発表時刻や予想比の良し悪しまでは無料データでは判定できないため、「本日決算発表があった銘柄はRSI条件を免除する」という簡易版の場中決算プレイに留めている
   - `config/daytrade-us.json` — 機能2（米国株版）の候補銘柄リスト（NYダウ30＋NASDAQ100構成銘柄、重複8銘柄を除いた計122銘柄）、`virtualCapitalYen`（別会計、100万円）、`maxPositionYen`／`marginMultiplier`（機能1と同じ意味）、`thresholds`（機能1と同じ意味だが`perMax`/`pbrMax`は存在しない）。1:2:6は円の配分比率（1/9:2/9:6/9）のまま。ウィブル証券の端株取引（フラクショナルシェア）を前提に金額指定注文としてモデル化し、予算をドル1単位まで使い切ったうえで0.00001株単位まで端数のまま発注する
   - `config/daytrade-crypto.json` — 機能3（暗号資産版）の候補銘柄リスト（GMOコイン現物取引「販売所」の取扱銘柄のうちYahoo Financeで円建て〈`-JPY`〉ティッカーが実在確認できた16銘柄）、`virtualCapitalYen`（別会計、100万円）、`maxPositionYen`／`marginMultiplier`（機能1と同じ意味）、`thresholds`（機能2と同じ形）。1:2:6は機能2と同じ円の配分比率のまま、為替換算は不要。機能4はこの候補16銘柄をそのまま流用する（別途configファイルは持たない）
   - `config/daytrade-cheap.json` — 機能1の`--profile=cheap`用、`maxUnitCostYen`（1単元の取得コスト上限、デフォルト10万円）のみ
   - `config/daytrade-highbudget.json` / `config/daytrade-us-highbudget.json` / `config/daytrade-crypto-highbudget.json` — 機能1/2/3それぞれの`--profile=highbudget`用、`virtualCapitalYen`（300万円）のみを上書き

3. **ローカルでの動作確認**（各機能で共通のパターン）
   ```
   npm run daytrade:dry-run:morning   # Discord送信なしで内容をログ出力
   npm run daytrade:run:morning       # 実際にDiscordへ送信
   ```
   同様に`afternoon`版、米国株版は`daytrade-us:dry-run`/`daytrade-us:run`、暗号資産版は`daytrade-crypto:dry-run`/`daytrade-crypto:run`（セッション引数はなし。15分おきに呼ばれる想定で、通知するかどうかは実行時刻ではなく`--dry-run`時も含め`lastNotifiedAt`からの経過時間で内部判定する。手動で通知パスを強制的に試したい場合は`tsx src/features/daytrade-sim-crypto/index.ts --notify`）、22戦略比較ラボは`crypto-strategy-lab:dry-run`/`crypto-strategy-lab:run`、30戦略比較ラボは`us-strategy-lab:dry-run`/`us-strategy-lab:run`、日本株・低単価限定プロファイルは`daytrade-cheap:dry-run:morning`/`:afternoon`・`daytrade-cheap:run:morning`/`:afternoon`、予算300万円プロファイルは`daytrade-highbudget:dry-run:morning`/`:afternoon`・`daytrade-us-highbudget:dry-run`・`daytrade-crypto-highbudget:dry-run`（`:run`版も同様に存在）、日本株・戦略ラボは`jp-strategy-lab:dry-run`/`jp-strategy-lab:run`。

4. **GitHub Secretsの登録**（Settings → Secrets and variables → Actions）
   `DISCORD_WEBHOOK_DAYTRADE` の1つのみ。

5. 各ワークフローをActionsタブから `workflow_dispatch` で手動実行し、実際にDiscordへ届くことを確認してからcronを信頼する。

6. `npm run watchdog:morning` / `npm run watchdog:afternoon`（`scripts/watchdog-daytrade-sim.ts`）は、GitHub Actionsの`schedule:`トリガー自体が発火しない障害をワークフロー内のエラーハンドリングでは検知できないため、GitHub Actionsとは独立した経路（Windows Task Scheduler等）から`origin/main`上の状態ファイルを見て「今日のこのセッションが完了しているか」だけを確認する監視スクリプト。再実行はせず、未確認ならDiscordへアラートするだけ（自動リトライは問題を隠す方向に働きうるため、人が状況を見て`gh workflow run`する形を意図的に残している）。

## 暗号資産・22戦略比較ラボ（機能4、`src/features/crypto-strategy-lab/`）

機能3の売買規律を単独で検証するだけでなく、他の手法と比べてどうなのかを確かめる実験場。機能3と同じ候補16銘柄・同じ市場データに対し、手法そのものが異なる22戦略を評価し、それぞれ別会計の仮想元本100万円で並行運用する。ポートフォリオ層（`portfolio.ts`）は機能3の1:2:6ピラミッド専用ロジックとは別に、「1回の買いでbudgetJpy円分を買う」という汎用実装にしてあり、各戦略が自分の買い増し方針を`decide()`側で自由に決められる。

| 戦略 | 内容 |
|---|---|
| 逆張り（コントラリアン） | 機能3と同じ設計。前日比急落＋RSI・出来高の裏付け＋75日トレンド内で打診買い、急騰＋RSI過熱で利確、トレンド割れで手仕舞い |
| 順張り（トレンドフォロー） | 75日移動平均を明確（+2%）に上回り、かつ陽線なら押し目を待たず即買い。移動平均を下回ったら手仕舞い |
| 移動平均クロス（25日/75日） | 短期線が長期線を上抜けたら買い（ゴールデンクロス）、下抜けたら売り（デッドクロス） |
| ブレイクアウト（20日高値/安値） | 直近20日の高値を出来高付きで更新したら買い、20日安値を割ったら手仕舞い |
| ボリンジャーバンド逆張り | 20日移動平均±2σの下限バンドを割ったら買い、中央線まで戻ったら利確 |
| RSI単体逆張り | RSI14が30未満で買い、70超で売り。値動き%・出来高・トレンドを一切見ない素朴な比較用ベースライン |
| ドルコスト平均法（DCA） | 値動きを見ず、7日ごとに定額（約8,333円）を機械的に買い増す。含み益+50%到達時のみ利確、それ以外は損切りしない |
| グリッドトレード | 75日移動平均から3%刻みの仮想グリッドラインに触れるたびに買い増し、平均取得単価+4.5%で利確 |
| モメンタムランキング | 候補16銘柄の直近20日騰落率を比較し、上位3銘柄だけを均等配分で買う |
| 出来高スパイク検知 | 出来高が平時の3倍以上に急増し、かつ陽線なら順張り買い。75日移動平均を割ったら手仕舞い |
| MACD（12/26/9） | MACD線（EMA12-EMA26）がシグナル線を上抜けたら買い、下抜けたら売り |
| 一目均衡表（転換線/基準線クロス） | 転換線（9日）が基準線（26日）を上抜けたら買い、下抜けたら売り。雲は意図的に省略した簡易版 |
| ストキャスティクス | 売られすぎ圏（20以下）で%Kが%Dを上抜けたら買い、買われすぎ圏（80以上）で%Kが%Dを下抜けたら売り |
| ATRボラティリティブレイクアウト | 前日終値からATR（14日）の1.5倍以上動いたらブレイクとみなして買い、平均取得単価からATRの2倍下落したら損切り |
| VWAP乖離 | 20日出来高加重平均線（VWAP）から5%以上下に乖離したら買い、VWAPまで戻ったら利確 |
| 曜日アノマリー | 値動きを一切見ず、毎週月曜に買い金曜に手仕舞う |
| パラボリック消耗反転 | 25日移動平均比-15%以上＋RSI20未満という極端なパニック売りだけに反応して買い、+10%の反発かRSI70超で早期利確 |
| RSIダイバージェンス | 価格は下落もRSIは上昇（強気ダイバージェンス）で買い、価格は上昇もRSIは下落（弱気ダイバージェンス）で手仕舞う |
| 相対強弱ペア（BTC/ETH） | BTCとETHの75日トレンド比の相対パフォーマンスを比較し、出遅れている方が5%以上劣後したら買い。ロングオンリーの簡易ペアトレード |
| ケルトナーチャネル・ブレイクアウト | 25日移動平均±ATR14×2のチャネル上限を上抜けたら買い（順張り）、中心線を割ったら手仕舞い |
| 3本移動平均パーフェクトオーダー | 短期(10日)＞中期(25日)＞長期(75日)の「パーフェクトオーダー」が新規成立したら買い、並び順が崩れたら手仕舞い |
| 心理的節目（ラウンドナンバー）反発 | 価格の桁数に応じたキリのいい価格帯の直上（支持線）にいたら買い、次の節目（抵抗線）接近で利確 |
| バイ・アンド・ホールド（BTC-JPY一点集中） | BTC-JPYに元本の95%を一点集中投下し、一度買ったら二度と売らない。他の戦略が「何もしない」より優れているかを測るベンチマーク |

税金は機能3と同じ理由（雑所得・累進課税）で計算せず、常に税引き前の損益で比較する。手数料モデル（GMOコインのスプレッド近似）も機能3と同じ。チェックは機能3と同じく15分おきだが、Discord通知は一切せず、ダッシュボード（`docs/crypto-strategy-lab/`）の更新のみを約1時間おきに行う（`data/crypto-strategy-lab-meta.json`の`lastPublishedAt`で間引く）。

機能5と同じ指値/成行PendingOrder化は意図的に見送っている: 機能5は1日1回・確定済みの終値を見て判断するため、その終値でそのまま即約定させると「見た値段ではもう買えない」look-ahead問題が発生する。機能4は同じ判断ロジックだが15分おきに再チェックしており、その`dayClose`はほぼリアルタイムに更新され続ける値のため、look-ahead問題は実質的に存在しない。

## 米国株・30戦略比較ラボ（機能5、`src/features/us-strategy-lab/`）

機能2と同じ候補122銘柄（`config/daytrade-us.json`をそのまま流用）・同じ市場データに対し、手法そのものが異なる30戦略を評価し、それぞれ別会計の仮想元本$10,000で並行運用する。USD建て一本で運用し為替を一切扱わない（売却時に実在するSEC Fee・FINRA Feeは機能2の実装を再利用する）。22戦略ラボと同じ汎用ポートフォリオ層を踏襲し、指標計算（`indicators.ts`）は資産クラス非依存のため`crypto-strategy-lab/indicators.ts`をそのまま再利用している。

30戦略のうち22本は22戦略ラボと同じ手法をUSD向けに移植したもの（相対強弱ペアだけは対象をBTC/ETHからGOOGL/GOOG〈同一企業の異なる株式クラス〉に変更）。残り8本は米国株ならではの新規戦略:

| 戦略 | 内容 |
|---|---|
| ゴールデンクロス/デッドクロス（50日/200日） | 50日移動平均が200日移動平均を上抜けたら買い、下抜けたら売り。6か月分の日足では計算できないため`fetchDailyHistory`の取得期間を1年に延長した |
| 長期高値ブレイクアウト（約200日高値） | 約200営業日（およそ1年）ぶりの高値を出来高付きで更新したら買い、20日安値を割ったら手仕舞い |
| ギャップフェード（寄り付きギャップ埋め） | 前日終値比3%以上の下方ギャップで寄り付いたら、値幅を埋め戻す反発を狙って買い。+4%で利確、-6%で損切り |
| 連続陰線押し目買い | 3営業日連続で陰線が続いたら機械的に買い、陽転かつ含み益が出ていたら手仕舞う |
| 低ボラティリティ選好 | 候補122銘柄をATR14/終値の比率で比較し、最も穏やかな上位5銘柄だけを均等配分で買う |
| 値幅ロト（本日の最大値動き銘柄） | 候補122銘柄の中でその日いちばん値動きが激しかった1銘柄だけを買い、翌営業日には無条件で手仕舞う |
| バイ・アンド・ホールド（NVDA一点集中） | NVDAだけに元本の95%を一点集中投下し、一度買ったら二度と売らない |
| ランダムウォーク（ベンチマーク） | テクニカル指標を一切見ず、未保有なら5%の確率で買い、保有中なら5%の確率で売る純粋なコイントス |

**約定タイミングの現実性**: 全30戦略の買い・売りシグナルは即座に約定させず、いったん`PendingOrderLab`（`types.ts`）として発注（キューイング）だけ行い、実際の約定は次回実行時（翌営業日）に持ち越す。

- **成行（既定）**: 翌営業日の始値で無条件に約定する。ブレイクアウト・クロス系はこちら
- **指値**: 戦略が明示的な目標価格を計算している6戦略（ボリンジャーバンド逆張り・VWAP乖離・グリッドトレード・心理的節目反発・パラボリック消耗反転・連続陰線押し目買い）のみ、その価格に本物の指値注文として発注する。翌営業日の安値がその指値以下まで下がった回にだけ約定し、安値が指値まで届かなければ約定せずそのまま指値を維持し続ける（`LIMIT_ORDER_EXPIRY_DAYS`=10営業日で失効）

ダッシュボードには発注済みだが未約定の注文数（`pendingOrderCount`）を「発注中」列として表示する。この`PendingOrderLab`方式は暗号資産・22戦略比較ラボにはまだ適用していない。

米国株の日足データは1日1回しか更新されないため、機能4のような15分おきのチェックは不要——機能2と同じく1日1回の実行で完結する（`.github/workflows/us-strategy-lab.yml`、機能2の20:20 UTCと5分ずらした20:25 UTC）。GitHub Actionsの`schedule`トリガーは遅延・欠落することがあるため、Windows Task Scheduler（`UsStrategyLabTrigger`）から`gh workflow run us-strategy-lab.yml`を叩く形で信頼性を補っている。同日にcronとタスクスケジューラが重複発火しても、`data/us-strategy-lab-meta.json`の`lastRunDate`で同日の二重売買処理を防ぐ。米国株の実現益は機能2と同じ20.315%のフラット税率で計算できるが、このラボは為替を扱わず米国株単体の比較に徹する実験場という位置づけのため、22戦略ラボと足並みを揃えて税金は計算せず、常に税引き前の損益で比較する。

state（`data/daytrade-sim-cheap-state.json`）・ダッシュボード（`docs/daytrade-sim-cheap/`）・GitHub Actionsワークフロー（機能1と全く同じcron時刻）・Windows Task Scheduler（`DaytradeSimCheapTriggerMorning`/`Afternoon`）はすべて機能1の既定プロファイルとは別に持ち、別会計の仮想元本100万円で並行運用する。同じ`DISCORD_WEBHOOK_DAYTRADE`チャンネルに投稿するため、Discord embedのタイトルに`（1単元100,000円未満）`という接尾辞（`profileLabel`）を付けて見分けられるようにしている。

## 予算バリエーション（`--profile=highbudget`、日本株・米国株・暗号資産の3本すべて）

機能1（日本株）・機能2（米国株）・機能3（暗号資産）それぞれに、総予算（`virtualCapitalYen`）だけを引き上げた並行インスタンス。既定プロファイルは元本100万円、highbudgetプロファイルは元本300万円（`config/daytrade-highbudget.json`・`config/daytrade-us-highbudget.json`・`config/daytrade-crypto-highbudget.json`、いずれも`virtualCapitalYen`の1フィールドのみを持つ小さな上書き用config）。候補銘柄・thresholds・1銘柄あたりの取得コスト上限（`maxPositionYen`）はすべて既定プロファイルと完全に同一のまま据え置く——変えるのは総予算だけ、という点が実験の要。

1銘柄あたりの上限を変えずに総予算だけを増やすと、複数の候補が同時にシグナルを出したときに「現金が足りず新規シグナルを見送る」頻度が減り、同時保有可能な銘柄数が増える。特に日本株版は総予算100万円・1銘柄上限35万円で同時に2〜3銘柄までしか持てない設計のため、この効果が最も出やすいはずという想定。米国株版・暗号資産版は総予算100万円・1銘柄上限10万円（同時に最大10銘柄前後）なので、日本株版ほど劇的な差は出ないと予想されるが、3本まとめて比較することで「総予算に対する1銘柄上限の比率」がリターンにどう効くかも横断的に見える。

Discord embedタイトルには`（元本3,000,000円）`という接尾辞を付けて見分けられるようにしている。

## 日本株・戦略ラボ（機能6、`src/features/jp-strategy-lab/`）

資金管理（¥3,000,000を¥500,000×6枠に分散）と決済ルール（IFD-OCO/OCO注文により±¥20,000で機械的に利確/損切り、リスクリワード1:1・勝率51%あれば理論上資産が増える設計）は明確な仕様に基づき、エントリーシグナルは機能1のルール1（前日比急落＋RSI・出来高裏付け＋75日移動平均トレンド内）をそのまま流用している——「押し目を待つ」逆張り哲学と相性がいいという判断。決済だけが機能1と異なり、%ベースではなく絶対円額の固定ブラケット（`(dayClose - avgEntryPriceJpy) * quantity`が±¥20,000に達したら理由を問わず手仕舞う）。

候補銘柄は機能1と同じconfig/daytrade.jsonの527銘柄をそのまま流用（別途configは持たない）。「1単元（100株）が¥200,000〜¥500,000前後」という指定は、cheapプロファイルと同じ考え方で実行のたびに現在値から動的に判定する。新規建ての枠数（同時に最大6銘柄）は、単一銘柄のスナップショットだけでは判定できない「戦略全体で今何銘柄持っているか」という情報が必要なため、このラボの`Strategy.decide()`シグネチャは他のラボにはない第4引数`openPositionCount`を持つ。約定タイミングは指値/成行のPendingOrder方式（買いは急落確認価格に指値、売りは翌営業日始値の成行）を最初から採用している。スプレッド・売買手数料は意図的にモデル化していない——国内株式売買手数料は原則無料（いわゆるゼロ革命）のため、手数料ゼロは実態に即した前提。

このラボは日本株版の他の戦略と違い1日1回のみの実行（TSE大引け後15:35 JST）——スイングトレード（数日〜数週間の保有）は前場・後場を区別する必要がないため、機能1と違いイントラデイのスナップショットを使わず、機能2/3と同じ`fetchDailyHistory`のみで完結する。「1つしかないのにドロップダウンやランキング表があるのは見づらい」という理由から、`docs/jp-strategy-lab/index.html`は`data.json`の`strategies.length`を見て表示を自動切り替えする——1本のときはdaytrade-simと同じ「カード＋資産推移グラフ＋ポジション/履歴テーブル」の単一ダッシュボード風、2本以上になったら元のラボ風（ランキング表＋ドロップダウン）に自動で戻る。

## daytrade-simの売買ルール一覧

Discordの売買通知は簡潔にするため、発動したルール名だけを表示する（詳細な閾値・数値根拠はこの表と`src/features/daytrade-sim/rules.ts`を参照）。

| ルール | 内容 | 実装上の条件 |
|---|---|---|
| ルール1 | 朝の急落は買い（打診買い）／朝の急騰は売り | 前場引け時点の下落率が`thresholds.morningCrashPct`以上なら新規買い（1段階目＝打診買い）。保有中に上昇率が`thresholds.morningSurgePct`以上なら利益確定売り |
| ルール2 | 急騰は買わない・追わない | 急落条件を満たさない限り新規買いはしない |
| ルール3 | 朝の急落でもパニック売りしない | 保有中に朝の急落が起きても、機械的なストップロス／トレンド割れ決済以外では売らない |
| ルール3/4/7 | 方向感のない日・もみ合いは休む | 前日比の値動きが`thresholds.flatDayPct`未満なら新規売買を見送る |
| ルール8 | もう一段跳ねたら利確 | 保有中に午後の上昇率が`thresholds.afternoonSurgePct`以上、かつRSI14が`thresholds.rsiSellConfirmMin`以上なら利益確定売り |
| RSI・出来高フィルタ | 急落の裏付け確認 | 新規買いはRSI14が`thresholds.rsiBuyConfirmMax`未満（本日決算発表があれば免除）かつ出来高が平時の`thresholds.volumeRatioMin`倍以上でないと入らない |
| PER/PBRフィルタ | 割高銘柄の除外 | PERが`thresholds.perMax`、PBRが`thresholds.pbrMax`を超える銘柄は新規買い対象外（データ取得失敗時はfail-openで通過） |
| 1:2:6ピラミッディング | 打診買い→追撃買い→本買い | 1段階目（急落確認時の打診買い）→2段階目（含み益が`thresholds.tranche2ConfirmPct`到達で追撃買い）→3段階目（RSI14が50超で本買い）。同じ日に2段階買い増しはしない。1:2:6は円の配分比率ではなく100株＝1口とした口数の比率（1段階目=1口・2段階目=2口・3段階目=6口）で、端数株は発注しない。各段階の購入時、その銘柄の取得コスト累計が`maxPositionYen`を超える場合はその回の購入を丸ごと見送る（部分約定はしない） |
| 安全装置: ストップロス | 機械的損切り | `thresholds.stopLossPct`が0より大きい場合のみ有効（デフォルト無効）。平均取得単価比の下落率がこの閾値を超えたら強制手仕舞い |
| トレンドフィルタ | 下落トレンド中の銘柄は買わない | 株価（終値）が75日移動平均を下回っている銘柄は、他の条件を満たしても新規買いしない |
| トレンド割れ決済 | 買った後にトレンドが崩れたら手仕舞い | ストップロス（`thresholds.stopLossPct`）とは独立で常時有効。保有中に株価が75日移動平均を`TREND_BREAK_BUFFER_PCT`（3%、`rules.ts`内の定数）超下回ったら、含み損益にかかわらず機械的に売る |
| 場中決算プレイ | 決算発表当日の特例 | 本日決算発表があった銘柄はRSI確認条件を免除 |

実際に投資手法として通用するかを検証する目的のシミュレーターであるため、閾値は感覚でチューニングせず（過去の値動きへの過学習になる）、実運用に近づける方向でのみ調整する。現時点で織り込んでいるコスト: 立花証券e支店の現物「定額手数料コース」を想定し、1日の約定代金合計（買い＋売り、複数銘柄込み）に応じた税込フラット料金（12万円まで無料、以降20万円まで176円・50万円まで253円・100万円まで506円・200万円まで759円…1,000万円まで2,783円、それ以降は100万円増すごとに253円加算。出典: [立花証券e支店 手数料ページ](https://www.e-shiten.jp/TorihikiRule/cost/)）を、その日最後のセッション（afternoon）でまとめて1回だけ控除する（`src/features/daytrade-sim/portfolio.ts`の`calcDailyCommission`）。実現益（勝ちトレードのみ）には20.315%（所得税15%＋復興特別所得税0.315%＋住民税5%）の源泉徴収税を都度適用（同ファイルの`TAX_RATE_ON_GAINS`、年間の損益通算は考慮しない簡易モデル）。未対応: `SPCX`など海外上場銘柄の前場/後場ロジック（対象外として許容）。

## 約定タイミングの現実性（日本株版・米国株版）

引け後に注文を出しても、もう終わったセッションの値段では買えない。シグナルは即座に約定させず、`PendingOrder`（`src/features/daytrade-sim/types.ts`）として一旦キューに積み、**次に実際に取引可能になった時点の始値**で約定させる方式にしている。

- **日本株版**: 前場のシグナル（前場引けの値段を見て判断）は、同じ日の後場寄り（`afternoonOpen`）で約定。後場のシグナル（大引けの値段を見て判断）は、翌営業日の寄り付き（`dayOpen`）で約定。前場・後場どちらの実行でも、まずその時点の適切な始値で前回分の未約定注文を約定させてから、新しいシグナルを判定してキューに積む、という2段階の処理になっている
- **米国株版**: 1日1回しかセッションがないため、シグナルは常に翌営業日の始値で約定。為替レートも約定日に取得し直した`fxRate`を使う
- **暗号資産版は対象外**: 24時間365日取引されるため「引けが終わって注文できない」状況が原理的に存在せず、直近の値動きをそのまま執行価格として使っても現実との乖離は小さい

キューに積まれただけでまだ約定していないシグナルは、Discord通知の別フィールドとWebダッシュボードの専用セクションに表示される。

**成行から指値への発展（日本株版・機能1のみ）**: tranche1（急落を確認しての打診買い）だけは本物の指値注文になっている。急落を確認したその価格（`inputs.dayClose`）に指値を置き、次セッションの安値（`morningLow`/`afternoonLow`）がその指値以下まで下がった回にのみ約定する。安値が指値まで届かない間は同じ銘柄への新規判断を行わず発注済みのまま持ち越し、`LIMIT_ORDER_EXPIRY_DAYS`（10営業日）経過で失効させる。tranche2（追撃買い）・tranche3（本買い）は成行のまま。売り注文（利確・トレンド割れ決済）もすべて成行のまま。

Discord通知には資産評価額（現金＋保有ポジション時価）の推移を折れ線グラフにした画像も添付される（直近30回分をチャート化）。保有ポジションがある場合は、銘柄ごとの時価内訳を示す円グラフも別embedとして投稿される。どちらも[QuickChart.io](https://quickchart.io/)で画像化しており、`POST /chart/create`で固定長の短縮URLを発行してから使う方式（`image.url`が長くなりすぎるとDiscord側に`400 Bad Request`で拒否されるため）。このリクエストが失敗した場合はグラフなしでレポート本体は通す（fail-open）。

Discordのembed（1024文字/画像URL長など）に縛られないダッシュボードとして、`docs/`を静的サイト化し[Cloudflare Pages](https://pages.cloudflare.com/)（実体はWorkers＋`[assets]`、`wrangler.toml`参照）にデプロイしている。実行のたびに各機能の`dashboard.ts`が`docs/<機能>/data.json`を書き出し、`index.html`がクライアントサイドでfetchしてChart.jsで描画する。`docs/index.html`が各ダッシュボードへのハブページで、個々のダッシュボードページ側は「← ダッシュボード一覧に戻る」という単一リンクのみを持つ。新しいダッシュボードを追加する際は`docs/index.html`のカードに1行追加するだけでよい。

> **Cloudflareの自動デプロイに関する注意**: 各ワークフローの状態コミット（`chore: update daytrade-sim state`等）はCloudflareのGit連携ビルドも監視対象にしており、コミットメッセージにCI-skipの目印文字列（角カッコで囲んだ`skip ci`）が入っていると、GitHub Actions側のCI（`ci.yml`）だけでなくCloudflareのデプロイも一緒にスキップされる。データだけの自動コミットを毎回`ci.yml`で型チェック・テストし直すコストと引き換えに、いずれの状態コミットもこの目印を付けていない。この目印文字列は単なるコミット本文中の部分一致で判定されるため、それを説明する文章であっても、コミットメッセージやコメントに角カッコ付きでそのまま書かないこと。

## 日本株版・米国株版・暗号資産版の違い

基本の売買規律（相場の8箇条・RSI/出来高フィルタ・75日移動平均トレンドフィルタ／トレンド割れ決済・1:2:6ピラミッディング）は3つとも共通（`src/features/daytrade-sim-us/rules.ts`と`daytrade-sim-crypto/rules.ts`はほぼ同一）だが、以下は意図的に異なる、または省略している。

| 項目 | 日本株版 | 米国株版 | 暗号資産版 |
|---|---|---|---|
| セッション | 前場引け／大引けの1日2回、平日のみ | 連続取引につき1日1回、前日終値比の`dailyMovePct`のみで判定、平日のみ | 15分おきに`dailyMovePct`判定、曜日制限なし。Discord通知だけは間引き、前回の通知から8時間以上経過したチェック回に限って送信する |
| 約定タイミング | `PendingOrder`としてキューに積み、次に取引可能になった時点の始値で約定 | 同様にキューに積み、翌営業日の始値（`opens.at(-1)`）で約定。為替レートも約定日に取得し直したものを使う | 対象外（据え置き） |
| 1:2:6の口数 | 単元株（100株）単位の口数比率 | 円の配分比率（1/9:2/9:6/9）のまま。フラクショナルシェア前提で0.00001株単位まで端数のまま発注する | 米国株版と同じ円の配分比率。satoshi相当（1億分の1）まで端数のまま発注 |
| PER/PBRフィルタ | あり | なし（米国株向けデータソース未整備のため対象外） | なし（暗号資産にPER/PBRの概念自体がない） |
| 場中決算プレイ | あり | なし | なし |
| 手数料・コストモデル | 立花証券e支店の定額手数料 | ウィブル証券の米国株手数料無料化を前提に、売却時のみSEC Fee・FINRA Fee/TAFを計上 | GMOコイン現物取引「販売所」を想定。手数料自体は無料だが、売値と買値のスプレッドが実質コスト（概ね1%程度の近似） |
| 為替 | 関係なし | 円→ドルの買い・ドル→円の売り、それぞれウィブル証券の両替スプレッド（税込15銭/ドル）を反映 | 関係なし（Yahoo Financeの円建て`-JPY`ティッカーをそのまま使用） |
| 実現益への課税 | 20.315%の源泉徴収を都度適用 | 為替差損益も含め同じ20.315% | 計算しない（雑所得・累進課税のため一律の税率でモデル化できない） |
| データソース | Yahoo Financeの日足チャートAPI＋Yahoo!ファイナンス公開ページ（PER/PBR/決算日） | Yahoo Financeの日足チャートAPIのみ | Yahoo Financeの日足チャートAPIのみ |

## データファイル

`data/daytrade-sim-state.json`（機能1の仮想ポートフォリオ＝現金・保有ポジション・実現損益・売買ログ・`pendingOrders`。`lastRunDate`＋`lastRunSession`は最後に完了したセッションの表示用、実際の二重処理防止は`lastMorningRunDate`/`lastAfternoonRunDate`をそれぞれ独立して見ている——後述の実装上の注意参照）、`data/daytrade-sim-us-state.json`（機能2、`lastRunDate`のみで二重処理防止）、`data/daytrade-sim-crypto-state.json`（機能3、`lastNotifiedAt`＋`lastNotifiedLogCount`でDiscord通知だけを間引く構造）、`data/crypto-strategy-lab-<戦略ID>-state.json`（機能4、22本、`data/crypto-strategy-lab-meta.json`に`lastPublishedAt`）、`data/us-strategy-lab-<戦略ID>-state.json`（機能5、30本、`data/us-strategy-lab-meta.json`に`lastPublishedAt`と`lastRunDate`）、`data/daytrade-sim-cheap-state.json`（機能1の`--profile=cheap`専用、既定プロファイルとは完全に別ファイル・別会計）、`data/daytrade-sim-highbudget-state.json`・`data/daytrade-sim-us-highbudget-state.json`・`data/daytrade-sim-crypto-highbudget-state.json`（機能1/2/3それぞれの`--profile=highbudget`専用、元本300万円）、`data/jp-strategy-lab-<戦略ID>-state.json`（機能6、`data/jp-strategy-lab-meta.json`に`lastPublishedAt`と`lastRunDate`）は各ワークフローが自動生成・コミットする。

## 実装上の注意（外部サイトの構造変更に備えて）

- デイトレード・シミュレーション（`src/features/daytrade-sim/`）はYahoo Financeチャートapiのイントラデイ版（`interval=5m&range=1d`）を使い、前場引け後（11:35 JST）・大引け後（15:35 JST）の1日2回バッチ実行して「前場の動き」「後場の動き」を近リアルタイムに検知する設計。`--session=morning`/`--session=afternoon`を実行時に渡す。前場引け・後場寄りの時刻は固定せず「11:30時点で最後に取引があったバー」「12:30以降で最初に取引があったバー」として拾っているため、TSEの取引時間がまた変わっても大きくは壊れない想定（ただしこの11:30/12:30という区切りはTSE上場銘柄の現地時間＝JST前提で、`config/daytrade.json`にNASDAQ上場銘柄等JST圏外の銘柄を混ぜると前場・後場の切り分けが機能しない）。ルールの判定閾値・RSI/出来高/PER・PBR/決算日/ストップロス/トレンドフィルタ/トレンド割れ決済/1:2:6の解釈は`src/features/daytrade-sim/rules.ts`にまとまっているので、通知される売買理由と食い違う場合はまずここを見る。日足の取得範囲（`marketData.ts`の`fetchDailyHistory`）は75日移動平均を安定して計算するため6ヶ月分取得している。Discordへの投稿は`sessionTrades`（このセッションで実際に約定した取引）または`failures`（銘柄データ取得失敗）がある場合に限定しており、`newlyQueued`（次セッション約定待ちのシグナル、まだ約定していない）だけでは投稿しない。default/cheap/highbudgetの3プロファイルとも同じ`index.ts`を共有しているのでこの挙動は3つとも同じ（US/暗号資産版は別ファイル）
- **二重処理防止の設計**: `lastRunDate`/`lastRunSession`は「最後に完了したセッション」しか記録しないため、GitHub Actionsの`schedule:`が数時間遅れて発火すると（ローカルのWindows Task Schedulerトリガーが正規の経路で、GitHub純正cronはあくまでバックアップ）、既に完了した別セッションの後に遅れて届いた重複実行が「別セッションだから」とガードをすり抜け、大引け後のデータを前場ラベルで再処理してしまう不具合が過去にあった（前場レポートが夕方に届く症状として顕在化）。`lastMorningRunDate`/`lastAfternoonRunDate`をそれぞれ独立して記録することで、どちらのセッションも「今日すでに完了したか」を実行順序に関係なく正しく判定できるようにしている（`types.ts`のコメント参照）。`scripts/watchdog-daytrade-sim.ts`も同じフィールドで確認する
- `scripts/watchdog-daytrade-sim.ts`: GitHub Actions自体の障害（スケジュール実行が発火しない）はワークフロー内のエラーハンドリングでは検知できない（そもそもジョブが起動しないため）ため、GitHub Actionsとは独立した経路で「今日のこのセッションが完了しているか」だけを確認する監視スクリプト。`origin/main`上の状態を見るだけで、再実行はしない（自動リトライは問題を隠す方向に働きうるため、人が状況を見て`gh workflow run`する形を意図的に残している）。GitHub Actions内で二重化しても同じ障害で道連れになるため、Windows 11のタスクスケジューラ等、GitHub Actionsの外側から`npm run watchdog:morning`/`watchdog:afternoon`を実行する運用を想定（土日はmarket closedとしてスキップ）
- PER/PBR・直近決算発表日（`src/features/daytrade-sim/fundamentals.ts`）はYahoo Financeのチャートapiではなく、`https://finance.yahoo.co.jp/quote/{symbol}`という個人向け公開ページのHTMLをスクレイピングして取得している（`v7/finance/quote`・`v10/finance/quoteSummary`など公式寄りのAPIはcrumb認証必須になっており無認証では使えなくなっていることを確認済み）。クラス名がCSS Modulesのハッシュ付きで壊れやすいため、`parseValuation`/`parseLatestEarningsDate`をfixtureでユニットテストしている（`test/features/daytrade-sim/fundamentals.test.ts` / `test/fixtures/yahoo-finance-jp-quote-*.html`）。取得に失敗してもPER/PBR絡みのフィルタは素通し（fail-open）になるだけで、他の判定は継続する
- 米国株版デイトレード・シミュレーション（`src/features/daytrade-sim-us/`）は日本株版と同じYahoo Financeチャートapiの日足エンドポイント（`fetchDailyHistory`はモジュールをまたいで再利用、銘柄コードに依存しないため変更なしで動く）と、為替レート取得専用の`JPY=X`という特殊ティッカーを使う（`fetchUsdJpyRate`）。`.github/workflows/daytrade-sim-us.yml`のcronはUTC固定（`20 20 * * 1-5`＝20:20 UTC）だが、米国の夏時間/冬時間切り替え（年2回）でJST換算の実行タイミングが前後1時間ずれる（EDT基準の設定のため、冬時間中は市場引けの約80分後の実行になる）。1日1回のバッチであり実害は小さいと判断し、現時点では季節ごとのcron出し分けはせず据え置いている
- 暗号資産版デイトレード・シミュレーション（`src/features/daytrade-sim-crypto/`）も同じ`fetchDailyHistory`をそのまま再利用しているが、Yahoo Financeの`BTC-JPY`のような`-JPY`ティッカーが直接円建てで返ってくることを利用しており、米国株版と違って為替換算のステップ自体が存在しない。GMOコインの取扱銘柄でもYahoo Financeに`-JPY`ティッカーが存在しない銘柄は候補から除外している（`config/daytrade-crypto.json`の`note`参照）。暗号資産は土日を含め取引が休まないため、`.github/workflows/daytrade-sim-crypto.yml`のcronは日本株版・米国株版と違い曜日指定なし（`*/15 * * * *`）で15分おきに実行する。ルール判定（`decideTradeCrypto`）は米国株版の`decideTradeUs`とほぼ同一実装で、実行のたびに評価される——ただし`canPyramidToday`（`lastTrancheEntryDate(position) !== today`）が同日内の追撃買いを防ぐ。通知は固定時刻ではなく`state.lastNotifiedAt`からの経過時間が`NOTIFY_INTERVAL_HOURS`（`index.ts`、8時間。24を割り切るため通知時刻が日々ドリフトせず一定のリズムに収束する）を超えた回に限って送る。固定時刻にしなかった理由は、日本株版のcronで実際に何時間もの遅延が発生した経験から、固定時刻依存だとその回の通知がまるごと抜けるリスクがあると分かっていたため。通知時に送るのは「そのチェックだけの売買」ではなく`lastNotifiedLogCount`以降にログへ積み上がった全ての売買（`newTrades`）。Discordの折れ線グラフ用（`state.equityHistory`、8時間おきに1点）とWebダッシュボード用（`state.dashboardEquityHistory`、1時間おきに1点）は別々の配列として持ち、公開時刻も`lastNotifiedAt`と`lastDashboardPublishedAt`で別々に管理している
